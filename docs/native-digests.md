# Native Supernote Digest handoff

Status as of 18 October 2026. Reader 2.2.0 adds Android-only Digest actions and synced Reader highlights. The Reader handoff targets the separate Supernote Bridge app; it makes no AI request and does not write the native database directly. Desktop Reader does not expose Digest actions.

## Reader workflow

1. Select text in Reader.
2. Choose **Digest** for the Bridge quick-save flow, or **Digest with note…** to review the excerpt first. Both actions are Android-only. **Highlight** and **Copy** are available on all platforms.
3. **Digest with note…** shows a confirmation with the excerpt and available source information; check it and tap **Save Digest**. The first **Digest** use asks for one-time approval and shows the destination list; later quick saves use Bridge's configured default list.
4. Return to Obsidian. Reader reports a saved Digest only after a valid Bridge callback. A selected excerpt is also saved in the vault's `Reader Highlights` folder; this is a Reader annotation, not a native ink highlight.

Tap a saved highlight for its menu. **Copy** copies its recorded excerpt; **Remove highlight** removes only the Reader annotation. If this device has a matching saved receipt, choose **Open Digest** to open it in Bridge 0.6.0 or newer, then use the native Digest app's **Edit** action. If no local receipt is linked, the menu offers **Digest** and **Digest with note…** to create one. Overlapping highlights show separate excerpt choices. Long-press remains available for selecting text.

The four-action dock is independent of the Reader status bar. [Synthetic Chromium preview](screenshots/reader-selection-dock-synthetic.png) shows it with Paper's status bar hide rule enabled; it is layout evidence only, not device verification. Reader works without Sidebar. If you use Sidebar, install version 0.4.3 or newer for compatible gesture handling around the dock and saved-highlight controls; 0.4.3 was used in the checked Nomad flow.

The **Save quote to Obsidian** command/context-menu item remains a separate Markdown quote-collection action. Reader settings offer **Configure defaults** for Bridge and **Reconnect Quick Digest** if Bridge trust was revoked. If tapping Digest does not open Bridge, install or update the helper and retry; Android URI dispatch cannot confirm whether the app is installed.

The Digest request ID is deterministic for the same excerpt and source context. Reader stores request IDs and statuses per vault in local storage, not the excerpt or an account-wide ledger. Reader's `pending` means only that the URI was dispatched and no callback has arrived; reopening that same request lets Bridge inspect its durable ledger. Reopening for review/status is allowed, but attempting another provider insert for a request already marked `PENDING` or `UNCERTAIN` is forbidden. A saved request re-verifies its receipt; a cancelled request confirms no write and permits a fresh review and explicit Save; no ledger entry starts the first Save flow. The first Quick Digest use asks Bridge for one-time approval; after approval, quick saves use the default list configured in Bridge. Reader's Quick Digest secret and trust state are device-local and never go into synced plugin settings. If a client is revoked in Bridge settings, use Reader's **Reconnect Quick Digest** action to clear local trust so the next quick action can request approval again.

Ordinary Markdown works without Transcripts. Reader sends the vault-relative Markdown path, heading and nearby context as provenance for Bridge's manual source workflow. Managed transcript Markdown requires Supernote Transcripts v0.15, its version 1 `selectionProvenance` capability, a matching local mirror, and validated native file/page identities. The adapter can resolve pages while page chips are hidden. If that provenance is unavailable or cannot be resolved, Reader stops instead of treating the transcript as ordinary Markdown.

Reader highlights are separate Markdown annotation files, one per deterministic source-and-context identity, in `Reader Highlights`. They synchronize as ordinary vault files and never modify the source note or managed transcript. The visible quote and source remain readable; bounded hidden metadata stores the anchor and optional native page IDs. Reader paints only a unique quote with matching saved context, or the exact full text of a single-chapter note. Ambiguous or unresolved annotations remain available in the **Highlights** manager for review/removal; Reader does not guess a new location. Duplicate synced records with the same identity appear once. Removing an annotation does not delete or edit the corresponding native Digest.

The association between a Reader annotation and its native Digest receipt is stored per vault on the device that received the successful callback. It is not included in the synced annotation file, and the native row ID may not exist on another device. Thus **Open Digest** is available only where that local receipt is known; a synced highlight without a local receipt still offers Copy, Remove, and new Digest actions.

## Verification status and limits

The inspected Knowledge provider is version 1.00.147; behavior on other firmware versions is not established.

On the checked Nomad and Knowledge provider 1.00.147, live verification passed for Copy with clipboard restoration; highlight persistence, reopen and removal; first Quick Digest with explicit approval and acknowledgement; reopening that same request without another insert; a later trusted Quick Digest and acknowledgement; and detailed review using a non-default list while Bridge's default was off. The detailed entry's local receipt was acknowledged. Tapping its saved Reader highlight opened the same Obsidian dropdown used for selected text, and **Open Digest** opened that local entry. The detailed Bridge flow included a typed note, later visible and preserved in the native Keyboard annotation tab. Native **Edit** changed only the synthetic Digest excerpt to include `(edited)`; the Reader annotation retained its original excerpt. After that edit, reopening from the saved Reader highlight used the local receipt route for the same entry; it did not resend the original excerpt or issue another provider insert. Source Markdown and `.note` files were unchanged, and the flow made no AI request. A Chromium regression also verifies that Digest handoff paints the saved annotation immediately, without reopening Reader.

This verifies the checked device/provider combination only. Cleanup is complete: all three synthetic native Digest entries were deleted through the native UI, all three Reader highlights were removed, and the browser fixture was deleted after a source-hash check. Prior reading positions and clipboard state were restored. No ADB forwards or AI requests were used, and source files remained unchanged. The provider adds its own `unique_identifier`; native Digest source navigation requires an embedded reference in `.note`, which Reader and Bridge do not modify. Native Digest-to-notebook navigation remains unsupported. Bridge's **Open original notebook** action has not been verified. Exact ink mapping, native Cloud/Partner sync, rename handling and cross-device resolution remain unverified.

The helper is a separately installed Android app. Its APK update must preserve an existing installation; this does not establish compatibility with every device Knowledge provider.

## Research background

The documented Supernote plugin SDK still has no Digest creation API. `PluginNoteAPI.getLassoLinks()` reads Digest link type 6, which the official reference describes as read-only; documented link writers accept types 0 through 4. `PluginDocAPI` provides document-reading methods, and `PluginFileAPI.openFile()` does not list Markdown. The Reader therefore delegates this Android workflow to the separate helper instead of treating it as a plugin SDK feature.

Static inspection of Knowledge app 1.00.147 identified an exported provider with a candidate NOTE source and insert route. Controlled create/readback/UI checks now confirm a working path for that inspected version, but the provider is not a public API contract and other firmware may differ. The local Android provider contract is distinct from the KOReader harmonizer's self-hosted Personal Cloud MariaDB strategy. The harmonizer writes cloud `t_summary` records for EPUB/PDF input and does not establish local provider behavior or exact-position navigation.
