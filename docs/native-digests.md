# Native Supernote Digest handoff

Status as of 20 October 2026. Reader 2.2.1 offers one Android-only **Create Digest** action and synced Reader highlights. The Reader handoff targets the separate Supernote Bridge app; it makes no AI request and does not write the native database directly. Desktop Reader does not expose Digest actions.

The 2.2.1 source keeps the original excerpt when tapping **Create Digest** hides the menu and clears browser selection. Linked Highlights omit the creation action and retain **Open Digest**. The regression covers delayed managed provenance, Highlight persistence, payload creation, and the annotation before Bridge dispatch. Current 2.2.1 menu behavior is pending Nomad verification.

## Reader workflow

1. Select text in Reader.
2. Choose **Create Digest** for the signed Quick Digest flow. It is Android-only. **Highlight** and **Copy** are available on all platforms.
3. On first use, Bridge verifies the request and shows one standard Android permission dialog naming the vault and destination list. Allow saves the Digest and remembers trust on this device; Cancel makes no native write and Reader receives a cancelled outcome. Later signed requests from that Reader client save without Bridge interaction.
4. Bridge verifies the write and returns the saved receipt to Reader, which stays in front. A selected excerpt is also saved in the vault's `Reader Highlights` folder before handoff. The Highlight is a Reader annotation, not a native ink highlight. Authenticated failures return cancelled, uncertain, or saved outcomes as appropriate; uncertain writes cannot be retried. Open a linked Highlight's **Open Digest** action to view the native entry, then use its **Edit** control.

Tap a saved highlight for its menu. **Copy** copies its recorded excerpt; **Remove highlight** removes only the Reader annotation. If this device has a matching saved receipt, choose **Open Digest** to hand off through Bridge to native Digest details, then use the native app's **Edit** action. If no local receipt is linked, use **Create Digest** to create one. A linked highlight hides the creation action to prevent an accidental duplicate. Overlapping highlights show separate excerpt choices. Long-press remains available for selecting text.

The four-action dock is independent of the Reader status bar. [Synthetic Chromium preview](screenshots/reader-selection-dock-synthetic.png) shows it with Paper's status bar hide rule enabled; it is layout evidence only, not device verification. Reader works without Sidebar. If you use Sidebar, install version 0.4.3 or newer for compatible gesture handling around the dock and saved-highlight controls; 0.4.3 was used in the checked Nomad flow.

The **Save quote to Obsidian** command/context-menu item remains a separate Markdown quote-collection action. Reader settings offer **Reset Digest permission** to clear Reader's local pairing and allow Bridge to request authorization again. The Bridge settings URI opens the native Knowledge app. If tapping **Create Digest** does not open Bridge, install or update the helper and retry; Android URI dispatch cannot confirm whether the app is installed.

The Digest request ID is deterministic for the same excerpt and source context. Reader stores request IDs and statuses per vault in local storage, not the excerpt or an account-wide ledger. Reader's `pending` means only that the URI was dispatched; Bridge owns the durable write ledger and prevents another insert for requests already marked `PENDING` or `UNCERTAIN`. Bridge opens an existing locally saved row on a repeat request. The first signed Quick Digest request asks Bridge for one-time authorization; after approval, Quick saves use the valid saved default list or native **Uncategorized** when that list is unavailable. Reader keeps the Quick Digest setup secret per vault on-device and never puts it in synced plugin settings. Bridge accepts a matching setup secret from an already trusted client without showing the dialog again, even if Reader has not received a foreground save callback.

Ordinary Markdown works without Transcripts. Reader sends the vault-relative Markdown path, heading and nearby context as provenance for Bridge's manual source workflow. Managed transcript Markdown requires Supernote Transcripts v0.15, its version 1 `selectionProvenance` capability, a matching local mirror, and validated native file/page identities. The adapter can resolve pages while page chips are hidden. If that provenance is unavailable or cannot be resolved, Reader stops instead of treating the transcript as ordinary Markdown.

Reader highlights are separate Markdown annotation files, one per deterministic source-and-context identity, in `Reader Highlights`. They synchronize as ordinary vault files and never modify the source note or managed transcript. The visible quote and source remain readable; bounded hidden metadata stores the anchor and optional native page IDs. Reader paints only a unique quote with matching saved context, or the exact full text of a single-chapter note. Ambiguous or unresolved annotations remain available in the **Highlights** manager for review/removal; Reader does not guess a new location. Duplicate synced records with the same identity appear once. Removing an annotation does not delete or edit the corresponding native Digest.

The association between a Reader annotation and its native Digest receipt is stored per vault on the device that received the successful callback. It is not included in the synced annotation file, and the native row ID may not exist on another device. **Open Digest** sends the local request hash; Bridge resolves it only when its device-local ledger has a verified `SAVED` row. A synced highlight without a local receipt still offers Copy, Remove, and **Create Digest** actions.

The Bridge candidate was installed in place with its existing signing certificate and preserved app data, but it was not launched and actual native Digest creation remains unverified. No paid requests, native Digest writes, or publication occurred. No screenshot or automatic long-drag acceptance is claimed.

Historical live verification on Bridge 0.5.1/0.6.0 passed for the earlier first-use approval/callback flow, repeated saves, detailed review, and saved receipt opening plus native editing. It does not verify the current Bridge transparent handoff or first-use Android dialog. The current Bridge changes are awaiting device verification. A Chromium regression verifies that Reader paints the saved annotation immediately before Digest handoff, without reopening Reader.

This verifies the checked device/provider combination only. Cleanup is complete: all three synthetic native Digest entries were deleted through the native UI, all three Reader highlights were removed, and the browser fixture was deleted after a source-hash check. Prior reading positions and clipboard state were restored. No ADB forwards or AI requests were used, and source files remained unchanged. The provider adds its own `unique_identifier`; native Digest source navigation requires an embedded reference in `.note`, which Reader and Bridge do not modify. Native Digest-to-notebook navigation remains unsupported. Bridge's **Open original notebook** action has not been verified. The helper is a separately installed Android app. Its APK update must preserve an existing installation; this does not establish compatibility with every device Knowledge provider.

## Research background

The documented Supernote plugin SDK still has no Digest creation API. `PluginNoteAPI.getLassoLinks()` reads Digest link type 6, which the official reference describes as read-only; documented link writers accept types 0 through 4. `PluginDocAPI` provides document-reading methods, and `PluginFileAPI.openFile()` does not list Markdown. The Reader therefore delegates this Android workflow to the separate helper instead of treating it as a plugin SDK feature.

Static inspection of Knowledge app 1.00.147 identified an exported provider with a candidate NOTE source and insert route. Controlled create/readback/UI checks now confirm a working path for that inspected version, but the provider is not a public API contract and other firmware may differ. The local Android provider contract is distinct from the KOReader harmonizer's self-hosted Personal Cloud MariaDB strategy. The harmonizer writes cloud `t_summary` records for EPUB/PDF input and does not establish local provider behavior or exact-position navigation.
